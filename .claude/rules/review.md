# Multi-Agent Dialectical Review Process

## 触发场景

以下场景 MUST 启动多 subagent 辩证评审：
- 新功能设计 / 架构方案
- 安全相关变更（SSL 配置、证书验证、认证逻辑）
- 高风险重构（Pipeline 顺序、引用计数、连接池）
- 性能优化方案

## 辩证评审流程

### Phase 1：并行多视角分析

同时启动 3 个 subagent，各自独立分析：

**Agent A — 方案倡导者 (Advocate)**
- 提出最优实现方案
- 论证方案的优势、可行性、收益
- 给出具体实现路径和代码示例

**Agent B — 批判审查者 (Critic)**
- 找出方案中的漏洞、风险、边界问题
- 质疑假设：是否阻塞 EventLoop？ByteBuf 是否正确 release？是否有 SSRF 风险？Pipeline 顺序是否安全？
- 列出可能失败的场景

**Agent C — 替代方案者 (Alternative)**
- 提出完全不同的实现思路
- 对比各方案的 trade-off（性能、安全、复杂度）
- 评估对现有 Handler 链的侵入程度

### Phase 2：综合评估

1. **矛盾识别** — 三方观点的冲突点
2. **风险矩阵** — 按「影响程度 × 发生概率」排序
3. **决策建议** — 综合三方意见，推荐方案 + 理由
4. **遗留问题** — 需用户决策的选项

### Phase 3：用户确认

将评估结论呈现给用户，明确标注需要用户决策的选项，获得批准后进入实施。

---

## 本项目专项评估维度

### 安全变更
- [ ] 是否破坏了 Pipeline 的安全顺序（绕过认证/限流）
- [ ] 是否引入了新的 SSRF 向量
- [ ] 是否泄露了证书/私钥信息
- [ ] mTLS 模式是否在所有代码路径下都被强制执行

### Netty / 性能变更
- [ ] 是否在 EventLoop 中引入了阻塞操作
- [ ] ByteBuf retain/release 是否在所有路径平衡（包括异常路径）
- [ ] 新 Handler 是否与背压机制兼容
- [ ] 是否有潜在的内存泄漏（引用计数、连接未关闭）
- [ ] 是否有 JMH 基准对比数据

### 架构变更
- [ ] 是否符合「Handler 职责单一」原则
- [ ] 是否影响连接池与负载均衡的一致性
- [ ] 热加载变更是否保证无状态过渡（不丢弃已有连接/令牌桶）

---

## 严格性要求

- 三个 agent MUST 独立运行，不互相参考
- IF 三方一致认为有严重安全风险 → MUST 阻止实施，报告用户
- IF 变更影响 ByteBuf 引用计数 → MUST 在 Phase 1 提供完整的 retain/release 路径分析
- IF 变更影响 Pipeline 顺序 → MUST 验证每个 Handler 的前置条件仍然满足
